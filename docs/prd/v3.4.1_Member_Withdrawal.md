# 제품 요구사항 문서 (PRD): 회원 탈퇴 정책 및 프로세스 (v3.4.1)

## 1. 개요 (Overview)
본 PRD는 사용자가 서비스 이용 계약을 해지하고 회원을 탈퇴하는 절차와, 탈퇴 후 발생되는 데이터(개인정보 및 저작물)의 처리 방침 및 관리 프로세스를 정의합니다.
회원 탈퇴 시 사용자의 개인정보를 별도 분리 보관하여 보안을 강화하고, 사용자가 생성한 콘텐츠(프롬프트, 프로젝트)가 서비스 내에서 더 이상 노출되지 않도록 처리하여 프라이버시를 보호하는 것을 목표로 합니다.

## 2. 핵심 요구사항 (Key Requirements)

### 2.1. 회원 탈퇴 (User Withdrawal)
**목표**: 사용자가 스스로 계정을 삭제하고 서비스를 탈퇴할 수 있는 기능을 제공합니다.

*   **User Side (사용자)**
    *   **진입점**: `설정(Settings) > 프로필(Profile)` 페이지 하단.
    *   **UI/UX**:
        *   '회원 탈퇴' 버튼 제공 (실수로 누르지 않도록 배치 및 스타일 고려 - 예: 붉은색 텍스트 또는 버튼).
        *   **탈퇴 확인 모달 (Confirmation Modal)**:
            *   탈퇴 시 등록한 데이터(프롬프트, 프로젝트)의 처리 방침을 명확히 고지.
            *   **고지 내용**: "탈퇴 시 회원 정보 및 등록된 프롬프트와 프로젝트는 삭제 처리되어 복구할 수 없습니다. (실제 데이터는 내부 정책에 따라 일정 기간 분리 보관 후 파기될 수 있음 - 법적 요구사항에 따라 문구 조정 가능하되, 사용자에게는 '삭제 및 노출 중단'을 강조)"
            *   최종 확인을 위한 텍스트 입력(예: "탈퇴하기" 입력) 또는 재확인 체크박스 제공.
    *   **Process**:
        *   탈퇴 완료 시 로그아웃 처리 및 메인 페이지(또는 로그인 페이지)로 리다이렉트.

### 2.2. 데이터 처리 정책 (Data Handling Policy)
**목표**: 탈퇴한 회원의 데이터를 안전하게 처리하고 서비스 내 노출을 차단합니다.

*   **회원 정보 이관 (Data Migration)**
    *   `User` 테이블에서 해당 회원 정보를 삭제하고, `WithdrawnUser` (탈퇴 회원) 별도 테이블로 주요 정보를 이관합니다.
    *   **이관 데이터**: 사용자 ID(UUID), 이메일(해싱 또는 마스킹 권장), 가입일, 탈퇴일, 탈퇴 사유(수집 시).
    *   **목적**: 재가입 방지(필요 시), 법적 분쟁 대비, 통계 관리.

*   **리소스 노출 제한 (Resource Visibility)**
    *   **대상**: 탈퇴 회원이 생성한 **프롬프트(Prompts)** 및 **프로젝트(Projects)**.
    *   **처리 방식 (Soft Delete / Hiding)**:
        *   데이터를 물리적으로 즉시 삭제하지 않고, `is_deleted` 또는 `is_withdrawn` 플래그를 `True`로 업데이트하거나, 소유자 상태를 기반으로 필터링.
        *   서비스 전체(검색, 랭킹, 추천 등)에서 해당 리소스가 노출되지 않도록 차단.
    *   **팀 프로젝트 예외 처리**:
        *   탈퇴 회원이 'Owner'인 팀 프로젝트는 비공개 처리 원칙.
        *   단, 팀원이 존재하는 경우 소유권 이전 프로세스가 필요할 수 있으나, MVP 단계에서는 **"팀 프로젝트의 경우 오너십을 가지고 있는 프로젝트는 다른 유저에게 보이지 않도록 처리"** 원칙을 우선 적용.

### 2.3. 관리자 기능 (Admin Capabilities)
**목표**: 관리자가 탈퇴 회원 현황을 파악하고 관리할 수 있습니다.

*   **Admin Side (관리자)**
    *   **진입점**: `Admin Console > Users > Withdrawn Users` (신규 메뉴).
    *   **기능**:
        *   **탈퇴 회원 목록 조회**: 탈퇴한 회원의 목록 (마스킹된 이메일, 탈퇴일 등).
        *   **상세 정보**: 해당 회원이 생성했던 리소스 수(통계) 등 확인.
        *   **완전 삭제(Hard Delete)**: 필요 시(예: 데이터 파기 요청, 보관 기간 만료) 관리자가 데이터를 영구 삭제할 수 있는 기능 (Optional).

## 3. 기술적 고려사항 (Technical Considerations)

### 3.1. 데이터베이스 스키마 설계 (PostgreSQL)

*   **WithdrawnUser 테이블 (신규)**
    *   `id` (UUID, PK): 기존 User ID 유지.
    *   `email` (String): 재가입 방지용, 혹은 식별용. (개인정보 처리방침에 따라 Hash 저장 고려).
    *   `original_joined_at` (DateTime): 최초 가입일.
    *   `withdrawn_at` (DateTime): 탈퇴일.
    *   `reason` (Text, Nullable): 탈퇴 사유.
    *   `backup_data` (JSONB, Nullable): 필요 시 중요 정보 백업.

*   **기존 리소스 테이블 (Project, Prompt)**
    *   기존에 `is_deleted` 컬럼이 있다면 활용, 없다면 추가 고려. 
    *   또는 쿼리 시 `User` 테이블과 조인하여 존재하지 않는 유저(또는 `WithdrawnUser`에 존재하는 유저)의 리소스를 제외하는 로직 구현 필요.
    *   **성능 고려**: 조인 비용이 높을 수 있으므로, 탈퇴 시점에 비동기 워커(Worker)를 통해 해당 유저의 모든 리소스에 `is_visible=False` 또는 `is_deleted=True` 업데이트를 수행하는 Batch 처리를 권장.

### 3.2. 백엔드 (Backend API)
*   **POST /api/auth/withdraw**: 회원 탈퇴 요청 처리.
    *   트랜잭션 처리 필수: `WithdrawnUser` 생성 -> 리소스 플래그 업데이트 -> `User` 삭제.
*   **GET /api/admin/users/withdrawn**: 탈퇴 회원 목록 조회.

### 3.3. 환경별 데이터베이스 대응 전략 (Environment Strategy)
**현황**: Local 환경(Dev)과 Production 환경(Prod)의 데이터베이스가 분리되어 운영됨.

*   **마이그레이션 관리 (Migration Management)**
    *   `WithdrawnUser` 테이블 생성 및 기존 테이블 스키마 변경 스크립트(.sql)를 작성하여 버전 관리.
    *   **Local**: 개발 단계에서 스크립트 직접 실행 및 테스트.
    *   **Production**: 배포 시 검증된 SQL 스크립트를 Production DB에 실행.
*   **환경 변수 및 설정**
    *   각 환경의 `SUPABASE_URL` 및 `KEY`가 분리되어 있으므로, 배포 시 정확한 타겟 환경을 확인해야 함.
    *   Production 환경에서는 데이터 파괴(User 삭제) 작업 전 백업 절차를 권장 여부 검토.

## 4. 영향도 및 예외 사항 (Impact & Exceptions)
*   **팀 공유 프로젝트**: 탈퇴자가 팀의 Owner인 경우, 남은 팀원들이 프로젝트를 볼 수 없게 되는 문제가 발생할 수 있음. 본 PRD에서는 "다른 유저에게 보이지 않도록 처리"로 명시되었으므로, 팀원들에게도 접근이 차단되는 것이 기본 동작임. (추후 고도화 시 소유권 이전 기능 고려).
*   **공용 템플릿**: 탈퇴자가 만든 공개 템플릿이 이미 다른 유저 복제(Fork)하여 사용 중인 경우, 복제된 사본에는 영향을 주지 않아야 함.
*   **DB 환경 차이**: Local DB에서 기능 검증 완료 후, Production DB에 테이블 생성 스크립트를 누락하지 않도록 주의.
