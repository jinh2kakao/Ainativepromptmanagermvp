# PRD v1.4.0: 템플릿 고도화 및 프로젝트 기능

## 1. 개요 (Overview)
본 PRD는 템플릿 시스템을 고도화하고 새로운 "프로젝트" 기능을 도입하기 위한 요구사항을 정의합니다. 목표는 사용자에게 더 유연한 템플릿 선택 경험을 제공하고, 여러 프롬프트를 체계적으로 정리하고 연결할 수 있는 강력한 프로젝트 관리 도구를 제공하는 것입니다.

## 2. 템플릿 고도화 (Template Enhancements)

### 2.1. 카테고리별 다중 템플릿 지원
- **현재**: 직무 소분류당 하나의 템플릿만 존재.
- **변경**: 하나의 직무 소분류에 여러 개의 템플릿 지원.
- **UI**: 프롬프트 생성/수정 화면(Assistance Mode)에서 직무 카테고리 선택 시, 사용자가 사용 가능한 템플릿 목록에서 선택할 수 있도록 함.
    - 템플릿이 하나만 존재하는 경우: 자동으로 해당 템플릿 적용 (기존 동작 유지).
    - 여러 개가 존재하는 경우: 드롭다운 또는 모달을 통해 원하는 템플릿을 선택하도록 함.

### 2.2. 기본(Default) 템플릿 로직
- **관리자(Admin)**: 관리자는 각 직무 카테고리별로 템플릿을 관리할 수 있음.
- **기본 설정**: 관리자는 특정 템플릿을 "기본(Default)"으로 설정 가능.
- **로직**:
    - "기본"으로 설정된 템플릿이 있는 경우, UI에서 해당 템플릿이 미리 선택됨.
    - 만약 여러 템플릿이 "기본"으로 설정된 경우 (지양해야 하지만 발생할 경우), **가장 최근에 업데이트된(`updated_at`)** 템플릿을 기본으로 사용.
- **관리자 UI**:
    - 카테고리별 템플릿 목록 조회.
    - "기본" 상태 토글(Toggle) 기능.
    - 현재 활성화된 기본 템플릿을 시각적으로 표시.

## 3. 프로젝트 기능 (Project Features)

### 3.1. 프로젝트 구조
- **정의**: 프로젝트는 프롬프트들의 집합(Collection)입니다.
- **관계**: 사용자는 여러 개의 프로젝트를 생성할 수 있으며, 하나의 프로젝트는 여러 개의 프롬프트를 포함할 수 있습니다.
- **데이터 모델**:
    - `Project`: `id`, `title`, `description`, `owner_id`, `created_at`, `updated_at`.
    - `ProjectPrompt` (또는 Node): 프로젝트와 프롬프트 간의 연결. 플로우 뷰를 위한 위치 정보(x, y) 및 연결 정보(next_node_id) 메타데이터 필요.

### 3.2. 대시보드 및 내비게이션
- **사이드바**: 왼쪽 사이드바에 "프로젝트(Projects)" 메뉴 추가.
    - 위치: "대시보드" 하단 또는 최상위 섹션.
    - 아이콘: 폴더 또는 프로젝트 관련 아이콘.
- **대시보드**:
    - "최근 프로젝트" 섹션 또는 별도의 프로젝트 뷰 제공.
    - "새 프로젝트 생성" 기능 제공.

### 3.3. 프로젝트 UI/UX
- **리스트 뷰**: 프로젝트 목록 표시 (프롬프트 개수, 마지막 업데이트 등 메타데이터 포함).
- **상세 뷰 (캔버스/플로우)**:
    - **시각적 인터페이스**: n8n이나 일반적인 순서도와 같이 프롬프트가 노드(Node)로 표현되는 인터페이스.
    - **연결**: 사용자는 프롬프트들을 순차적 또는 병렬로 연결 가능.
    - **인터랙션**:
        - 캔버스에 프롬프트 드래그 앤 드롭.
        - 노드 클릭 시 프롬프트 상세 수정.
        - "실행(Run)" 버튼 (추후 기능 연동을 위한 자리 표시).
    - **디자인**: 현재의 "프리미엄 & 다이내믹" 디자인 시스템(글래스모피즘, 부드러운 애니메이션)을 준수해야 함.

### 3.4. 프로젝트 템플릿
- **요구사항**: 프로젝트 또한 직무 카테고리(대분류 기준)에 따른 "기본 템플릿"이 제공되어야 함.
- **사용 사례**: "마케팅"용 프로젝트 생성 시, 표준화된 프롬프트 흐름(예: "아이디어 도출" -> "카피라이팅" -> "검토")으로 미리 채워짐.
- **구현**:
    - `ProjectTemplate` 모델.
    - 프로젝트 템플릿(미리 정의된 프롬프트 세트 및 연결)을 정의하는 관리자 인터페이스.

### 3.5. 향후 확장성
- **API Key 관리**: 추후 사용자가 개인 API Key를 저장하고 관리하는 기능 연동 준비.
- **자동 실행**: 프로젝트에 정의된 흐름이 실제로 실행 가능해지며, 한 프롬프트의 출력을 다음 프롬프트의 입력으로 전달하는 기능 추가 예정.

## 4. 관리자 요구사항 (Admin Requirements)

### 4.1. 템플릿 관리
- 프롬프트 템플릿 생성/수정/삭제 UI.
- 기본(Default) 템플릿 설정 UI.
- 기본 템플릿 조회 및 필터링/강조 UI.

### 4.2. 프로젝트 관리
- 전체 사용자 프로젝트 조회 (모니터링용 읽기 전용).
- 프로젝트 템플릿 관리 (표준 흐름 생성).

## 5. 기술적 고려사항 (Technical Considerations)

### 5.1. 데이터베이스 변경
- 신규 테이블: `Project`, `ProjectNode` (또는 `ProjectItem`), `ProjectTemplate`.
- 업데이트: `PromptTemplate` (카테고리당 다중 템플릿 허용, 기본 설정 플래그 로직).

### 5.2. 프론트엔드
- 신규 페이지: `/projects`, `/projects/[id]`.
- 신규 컴포넌트: `ProjectCard`, `FlowCanvas` (React Flow 또는 커스텀 SVG/Canvas 라이브러리 활용), `TemplateSelector`.
- 사이드바 업데이트.

### 5.3. 마이그레이션
- 기존 프롬프트는 독립적으로 유지됨.
- 기존 `Prompt` 모델에 대한 변경(Breaking Change)은 없으나, 엄격한 소유권이 필요한 경우 `Prompt`가 `Project`를 참조해야 할 수 있음 (또는 매핑 테이블을 통해 느슨한 연결 유지).

## 6. 사용자 경험 (UX) 목표
- **직관성**: 플로우 빌더는 전체 IDE처럼 지나치게 복잡하지 않고 사용하기 쉬워야 함.
- **시각화**: 노드와 연결선에 대한 고품질 시각 효과.
- **매끄러움**: 프로젝트 뷰와 프롬프트 수정 뷰 간의 전환이 부드러워야 함.
